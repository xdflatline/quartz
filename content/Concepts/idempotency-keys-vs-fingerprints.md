## Definition

Both techniques solve the same problem: when a request fails before you know whether the server processed it, retrying naively risks executing the side effect twice (double-charge, double-booking, duplicate email). The two techniques attach a deduplication token to the request, but they differ in **who generates it** and **what space it lives in**.

| | Idempotency key | Fingerprint |
|---|-----------------|-------------|
| Generated by | **Client** | **Server** (hash of request fields) |
| Retrofit cost | High — both sides must support it | Low — server-only |
| Collision risk | UUID v7 — astronomically low | False negatives when two legitimate requests look identical |
| Where used | AWS APIs, Stripe, Adyen, PayPal | Pre-existing systems that can't add a client field |

## When to use each

Newman's prescription, sharpened by his Pragmatic Engineer interview:

- **Building a new API?** Use idempotency keys. The client generates a UUID (v7 — sub-microsecond collision risk), passes it in the request, and the server records the outcome against it. Subsequent retries with the same key replay the original result rather than re-executing.
- **Retrofitting an existing system that has no client-supplied idempotency field?** Fingerprints. Server hashes the request payload; if a recent duplicate exists, return the cached result. Limit the dedup window (5 min, 10 min, 1 hour) to bound memory.
- **Best of both?** Run fingerprinting *in addition* to idempotency keys. If the same key is replayed with different parameters, fingerprint divergence flags the request as a likely client bug and rejects it.

## Failure modes

- **Idempotency keys**: storage (must persist every key + outcome for the dedup window), TTL choice (Stripe uses ~24 hours), and the rare case where the client reuses a key for a *different* logical operation.
- **Fingerprints**: 
  - **False negatives** — Denmark payment example: two legitimate 40-kroner purchases in the same shop within minutes get the second rejected. Different amounts work fine.
  - **False positives (false acceptance)** — AWS example: provisioning 20 EC2 instances in a loop produces 20 identical requests; fingerprint-based dedup would silently drop 19 of them. Solutions: include a loop index or per-iteration nonce in the fingerprint input.
